# Mathematical validation and research claims

Audit date: September 10, 2026. CPU only; no new cloud compute or generation. Source runs and vendor code were read without modification.

**Verdict:** The application correctly connects saved outcome observations to the pinned Goodfire reconstruction implementation. The tested counts, cross-validation, point estimates, uncertainty calculations, and checkpoint boundaries agree with upstream, including the two completed Muse runs. This establishes implementation agreement for the tested paths. It does **not** establish that Muse achieves the paper's reported reconstruction accuracy, cost reduction, or fork-detection performance.

The suitable product claim is: **“Explore sampled outcome changes using Goodfire's released reconstruction method, with inspectable continuations and exact saved-trace refinement.”** Avoid “paper results reproduced on any model,” “statistically significant fork detected,” or an unconditional accuracy/savings multiplier.

## The actual mathematical contract

### Sampling and the plotted point

At checkpoint `t`, the unchanged prefix contains source tokens strictly before `t`. A candidate token `w` is then selected and included in the continuation's conditioning prefix. Enumeration uses the recorded temperature-1 probabilities, the selected top-k limit, the minimum probability threshold, and inclusion of the source token. The candidates' probabilities are normalized by their retained total mass `M_t`.

For each of the `S` scheduled observations, the app first draws a branch with probability `q_w = p_w / M_t`, then generates one new continuation. It groups those jobs by branch only for execution and restores their original draw order for counting. Every generated observation appears exactly once; there is no second answer resampling or probability reweighting. The observed category frequency is `count_k / S`.

If branch-conditioned continuations are independent draws under the recorded sampler, these observations have multinomial counts with outcome probabilities `o_t = Σ_w q_w o_t^(w)`. This matches the mixture construction described by the paper, while collecting only `S` total continuations rather than the release's `S` continuations **per branch**. It preserves the estimand but changes finite-sample variance and compute accounting compared with the fully stratified reference. [Paper §2](https://arxiv.org/html/2608.19611v1#S2).

Source: `sampling.allocation`, `sampling.position_draws`, `LiveService.collect`, upstream `enumerate_branches_at` and `otrecon.data`. The direct sampling design is recorded as `position_mixture_v1`.

### Segmentation, pooling, CV and coordinates

The app invokes upstream `M5a_segkernel` directly. For its multinomial variant, segment cost is `−Σ_k n_k log(n_k / Σ_j n_j)`, omitting likelihood constants that do not change partition selection. PELT uses this cost plus a penalty per extra boundary. Costs on the explicit count matrix and the exhaustive small-case optimum were independently checked.

Within a segment, prediction at token coordinate `t` uses:

`α_k(t) = 1/K + Σ_i exp(−(t−t_i)^2 / (2h^2)) c_ik`

`prediction_k(t) = α_k(t) / Σ_j α_j(t)`

Only observations in the selected segment contribute. The `1/K` pseudocount is present in actual upstream code and matters for unobserved categories. Nominal model bands come from the corresponding Beta marginals of this Dirichlet distribution. They are neither bootstrap intervals nor calibrated fork significance tests.

Cross-validation divides draw indices into five folds **at every observed position**, fits on the other folds, and scores held-out category counts with log-likelihood. It does not tune on the optional dense reference. The actual grid has 168 combinations: two cost variants, 12 penalties and seven widths. Uneven token spacing is passed in its original coordinates to the kernel. PELT segments observation indices; a boundary is displayed as the interval between its adjacent measured checkpoints, with midpoint only a plotting convention. Fits are displayed within measured support, not extrapolated over the entire response.

**Upstream prose/code discrepancy:** paper §2 describes cost selection as multinomial versus L2. The pinned released `SegmentKernelPool.grid()` searches **`mult` versus `linear`**, where `linear` fits weighted empirical-logit trends. L2 exists as a separate upstream detection option/ablation. The app follows released code. Its default-CV description must not claim that every fit uses the exact multinomial cost. [Paper §2](https://arxiv.org/html/2608.19611v1#S2), [pinned model implementation](https://github.com/ericb-goodfire/forking-fast/blob/d32fed8d4162a4888291c4b3a38b059727c85a41/otrecon/otrecon/models.py).

The current Muse original and refined fits both selected `mult`; penalties were 2 and 1 respectively, bandwidth 128 for both. No retrospective parameter changes were needed to recover their stored graphs.

### Reference and comparison metrics

The optional live dense reference collects fresh draws in a separate sampling phase. TV is `0.5 × Σ_k |prediction_k − reference_k|`; held-out log-likelihood uses reference observations. Neither optional reference nor cheap pass is an exact true distribution. The plotted model-band coverage metric counts containment of finite-reference category proportions; it is descriptive, not guaranteed coverage of unknown truth.

The custom-prompt app retains all user categories plus Other. Upstream benchmark preparation can collapse rare categories using a reference curve. This is another reason not to equate an arbitrary custom-prompt score with a paper figure. The live implementation appropriately does not use unknown high-sample outcomes to select categories.

## Material limitations for product presentation

| Severity | Finding | Consequence and recommended display |
| --- | --- | --- |
| High if misrepresented | A segmentation boundary is an estimator choice, not a significance test. | Use **candidate change interval**. Show adjacent counts, effect size and “refine this interval”; avoid success-colored “confirmed fork.” |
| High if hidden | Other combines capped, unparsed and ambiguous responses. The 10% cap gate is global and heuristic. | Keep these causes separately visible at every checkpoint and highlighted interval. Passing the gate cannot certify a decision fork. |
| High if misrepresented | The graph conditions on retained branch mass. Refinement retains as little as **83.737%**; original as little as **79.090%**. | Label estimates as retained-branch outcomes and show omitted mass near the graph, especially when inspecting differences. Renormalization does not recover omitted branches. |
| High if misrepresented | Model credible bands have no calibrated coverage guarantee; paper Appendix A reports 48–64% coverage for nominal 90% bands and recommends point estimates. | Keep model bands optional and clearly named; raw-count Wilson intervals answer a different, pointwise question. [Paper Appendix A](https://arxiv.org/html/2608.19611v1#A1). |
| Medium | Mention matching can label “I reject X” as X; it cannot recognize paraphrases or determine correctness. | Display the exact matcher, matched text, completion state and original reply. Avoid “correctness probability” unless a separate evaluator supplies correctness. |
| Medium | Refinement is chosen after seeing the original graph. | Treat it as exploration. Claims of a reliable boundary need fresh confirmation and an explicit hypothesis/testing plan. |
| Medium | Additional cost/penalty/kernel choices, category count, token cap and temperature change the measurement. | Preserve and expose settings and source lineage. A visually smoother line is not stronger evidence by itself. |
| Medium | Any-model support does not follow from estimator agreement. Generation defaults, tokenizer and completion channels are model-specific. | Describe tested model/revision capability; require a complete-output preflight for new models. |

A useful bound clarifies omitted mass: if `o_full = M × o_retained + (1−M) × o_omitted`, then `TVD(o_full, o_retained) ≤ 1−M`. Thus 83.737% retention allows a loose worst-case discrepancy of 16.263 percentage points in total variation. This is a bound from missing branches, not an estimate that the actual error is that large.

No arithmetic bug requiring a sampler or reconstruction-core edit was found within this audit. The material product risks are primarily claims, completion diagnosis, measurement scope and model compatibility.

## What the completed refinement establishes

The 320 saved observations yield **313 DELAY, two LAUNCH and five capped Other**. LAUNCH occurs once at 339 and once at 347; every other checkpoint has zero LAUNCH. Other occurs once each at 355, 371, 387, 403 and 427. The exact upstream refit returns intervals **347–355** and **427–435**. The first mixes a rare decision change with a cap category change; the latter concerns capped versus completed outcomes. The reconstruction code contains no hypothesis test certifying either interval.

The existing two-grid benchmark also provides no general offset advantage. Separate fits have mean TV 0.0303 / 0.0349 / 0.0408 at strides 4 / 8 / 16, versus 0.0280 / 0.0304 / 0.0350 for a half-stride uniform grid. Joint fits are approximately tied with the uniform grid. Actual draw counts and expected-token budgets differ slightly and are recorded; these are not exactly matched-token-budget results. This supports keeping additional passes optional and prioritizing a simple scan → inspect → refine workflow.
